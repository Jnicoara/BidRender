# Stage 2 audit — 2026-09-21

**Find and report. Nothing here was fixed.** Ordered worst first, where "worst"
means how much money or rework it costs to discover late rather than how hard
it is to fix. Each finding says how it was checked, because a claim in an audit
is worth exactly what the check behind it is worth.

**Confidence is marked.** `VERIFIED` means I ran it or read the code path end to
end. `INFERRED` means I read enough to be confident and not enough to prove it.
`UNTRACED` means I looked and stopped — it is listed so it is not mistaken for
a clean result.

## 1. CRITICAL — priced baseline rows are wiped on every startup

**VERIFIED.** `server/db.ts`, `backfillMaterialMetadata`, runs on every boot:

```js
if (Number(row.costPerUnit) !== Number(intended.costPerUnit)) {
  patch.costPerUnit = intended.costPerUnit;
}
```

It walks every **baseline** row (`userId IS NULL`) and rewrites `costPerUnit`
back to the seed's value. **The seed ships everything at $0.**

**So if the 1,783-row pricing list is written onto the baseline rows, every
price returns to $0 at the next deploy, silently.** Nothing errors, nothing
logs, and the catalog looks exactly as it did before anybody spent a weekend
pricing it. This is the single most expensive thing in this document and it is
one release away from happening.

**The safe path already exists and is the one to use.** `materials.importPrices`
forks a baseline before writing (`target.userId === null ? forkMaterial(...)`),
and forks are user rows, which this backfill never touches. Import through that
procedure and the prices survive.

**Note the asymmetry**, because it is a trap of its own: `laborHours` is NOT in
the backfill's list, so a labour unit set on a baseline row **does** survive
while a price set beside it does not. Two fields on one row behaving
differently is the kind of thing nobody predicts and everybody assumes is a
bug in whichever direction bit them.

**Also affected by the same pass:** `category`, `searchAliases`, `description`,
`trade` and `defaultQty` are all re-stamped from the seed on every boot. Editing
any of them on a baseline row is temporary.

## 2. Seats are sold but never counted

**VERIFIED.** There is no member limit anywhere — no `seatLimit`, no
`maxMembers`, no count check on invite or accept. `grep` across `shared/`,
`server/` and `drizzle/` returns only prose about the owner's single seat.

Tiers of 1, 5 and 15 users are therefore **unenforced**: a one-seat company can
invite fifteen people and nothing objects. `users.accessTier` is
`standard | internal` and is explicitly "a property of the PERSON, not of their
membership" — it is the internal-build flag, **not** a billing tier, and it
would be the wrong thing to overload.

**What is missing is small and specific:** a seat count on `companies`, a check
in the invite and accept paths, and a decision about what happens to the 12th
member when a company downgrades. That last one is the part worth deciding
before there is customer data, not after.

## 3. GOOD NEWS — the data model is already per-company, not per-user

**VERIFIED, and it is the opposite of the concern that prompted this audit.**

`server/_core/companyScope.ts` resolves, once per request:

```
dataUserId: membership.ownerUserId
```

Every data query filters on **the company owner's** user id, so two people at
one shop already see the same bids, catalog, assemblies and prices. The counts:

|                                           |                    |
| ----------------------------------------- | ------------------ |
| `scope.dataUserId` (shared, company-wide) | **530** call sites |
| `ctx.user.id` (the individual)            | **6** call sites   |
| `scope.actorUserId` (who is acting)       | 12 call sites      |

**All six individual uses are correct**: `authRouter` asking who am I, and
`onboardingRouter` ticking one person's checklist. Neither should be shared.

The access-control boundary is careful in the ways that matter — derived from
the authenticated user and never from anything the client sends, fails closed
rather than falling back to the user's own id, and a suspended membership bites
on the next request. Roles exist (`owner`, `admin`, `estimator`, `viewer`) with
capabilities per role.

**So the change for multi-user is not the data model. It is seats (§2) and the
docs (§4).**

## 4. Docs versus code — the findings that would mislead somebody

This is the section asked for explicitly: what a person would build wrongly if
they trusted what is written.

### 4a. "Everything is scoped by userId" — MISLEADING, and the expensive one

`CLAUDE.md` § Architecture, Data model: _"everything is scoped by `userId` with
cascade deletes"_.

**True of the schema, false of the app.** The column is `userId`; the value is
the company owner's id. Somebody reading that line reasonably concludes the
product is single-user and either rebuilds a company layer that already exists
or prices the product as if multi-user were a project. It is the same shape as
the OAuth sentence `references/deploying.md` § 8 calls the most expensive wrong
line in these docs — a sentence that makes a finished job look unstarted.

## 5. Pickers — CLEAN, no action needed

**VERIFIED.** Every surface that lists materials or assemblies reads the live
catalog through tRPC. There is no snapshotted or hardcoded list anywhere:

`MaterialPicker` (→ run-type picker, assembly builder) · `AssembliesLibraryPage`
· `MaterialsLibraryPage` · `MaterialDatabasePage` · `BidsPage` · `KitsPage` ·
`QuickBidPage` · `TakeoffPage` · `LaborRateQuickEdit`

**"If I add a material right now, does it show up with nothing else done?"
Yes.** No global `staleTime` is configured, so React Query's default of 0
applies and every one of these refetches on mount; the material mutations also
invalidate `materials.list` explicitly. A picker opened after the add gets the
new row.

One caveat, not a fault: `materials.list` defaults to `status: "active"`, so a
row added as archived would not appear. That is the intended behaviour.

## 7. Catalog seams

### 7a. CSV import versus the supplier-import design — 3 of 4

**VERIFIED** against `materialsRouter.importPrices`:

| Rule                                 | Status                                                                                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Match first                          | **Yes.** Case- and space-insensitive name match.                                                                                                        |
| Never auto-create                    | **Yes.** Unmatched rows are returned, never inserted, with the reasoning written out: a supplier sheet is full of items this contractor does not stock. |
| Link, don't replace                  | **Yes.** A baseline forks on write, so a shared row never carries one user's supplier price.                                                            |
| Review screen before anything writes | **NO.** The mutation writes as it goes and reports `{ priced, unmatched }` afterwards. There is no dry run.                                             |

The missing review step matters more now than it did: a 1,783-row import that
half-matches is not something to discover from a result object. The fix is a
`dryRun` flag returning the same shape without writing — small, and it makes
the fourth rule true.

### 7b. A retired material under a run type — HOLDS

**VERIFIED.** Retiring sets `isActive = false` rather than deleting.
`getMaterialsByIds` does not filter on `isActive`, so a run type pointing at a
retired material still resolves its name and still reads correctly on the
palette. It stops appearing in pickers, because `getLibraryMaterials` filters
active. That is the designed behaviour and it works.

### 7c. Duplicates from imports — GUARDED, but only for baselines

**VERIFIED.** `dedupeBaselineRows` runs at startup and deletes duplicate
`userId IS NULL` rows by name, keeping the lowest id. It does **not** dedupe
user rows, which is correct — a user's own two similar rows are their business.
The import cannot create duplicates anyway, since it never inserts (§7a).

### 7d. The startup re-stamp once many rows are forked — SCALES, but noisily

**VERIFIED by reading; not load-tested.** The re-stamp only touches
`userId IS NULL` rows, so forks are untouched and the work does not grow with
the number of forks. Two things to know:

- It issues **one UPDATE per changed row**, in a loop, not a batch. At 1,348
  baseline rows a first boot after a catalog change could be a thousand
  round trips. Correct, just slow, and it happens inside the seed lock.
- A second pass repairs **stale forks** — user rows with a NULL category,
  aliases or defaultQty — so that one DOES grow with the number of forks. With
  a company that has forked most of the catalog it is a second full scan.

Neither is a bug today. Both are worth knowing before the catalog trebles.
